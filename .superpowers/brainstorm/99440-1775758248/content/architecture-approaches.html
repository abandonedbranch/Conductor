Multi-Agent Orchestration: Three Approaches

How should Conductor coordinate sub-agents, shared context, and deterministic stitching?

A

Centralized Conductor

Conductor owns the full lifecycle. A single orchestration actor manages intent extraction, task decomposition, sub-agent dispatch, log aggregation, and stitching. Sub-agents are lightweight — just a LanguageModelSession + tools + a reference to the shared log.

Pros

  • Simple mental model — one place controls everything
  • Easy to debug and trace execution
  • Log consistency guaranteed by single owner
  • Closest to current architecture (evolutionary)

Cons

  • Conductor actor becomes large and complex over time
  • Sub-agents have no autonomy — can't self-organize
  • Adding new orchestration patterns means modifying the Conductor
B

Log-Driven Coordination

The structured log IS the coordination mechanism. Conductor extracts intent and writes a plan to the log. Sub-agents watch the log for their assignments, execute, write results back. A deterministic stitcher watches for completion signals and assembles the response. No central controller after the initial plan — the log drives everything.

Pros

  • Highly decoupled — sub-agents are truly independent
  • Log is the single source of truth (inspectable, replayable)
  • Sub-agents can read others' entries and self-steer
  • Natural fit for the "iterative with checkpoints" pattern you described
  • Adding new agent types doesn't touch orchestration code

Cons

  • Completion detection is harder — when is "done"?
  • Concurrent log access needs careful actor isolation
  • Debugging requires reading log traces rather than stepping through a controller
C

Hybrid: Conductor Plans, Log Coordinates

Conductor handles the bookends; the log handles the middle. Conductor does intent → plan → dispatch (deterministic). Sub-agents coordinate via the structured log (autonomous). Conductor deterministically detects completion (all tasks have success/error entries) and stitches. Clean separation: Conductor owns lifecycle, log owns coordination.

Pros

  • Best of both — clear lifecycle ownership + autonomous agents
  • Completion detection is simple (Conductor knows the task list, checks log)
  • Sub-agents still self-steer via log reads
  • Deterministic end-to-end except for intent extraction and tool arg translation
  • Matches the pipeline you described: intent → keywords → tool search → purpose groups → dispatch → log → stitch

Cons

  • Slightly more moving parts than pure centralized
  • Need clear boundaries for what Conductor vs. log controls

Recommendation: C (Hybrid)

Option C maps directly to what we discussed. The Conductor is lean (intent + dispatch + stitch), sub-agents are autonomous (tool calls + log writes + self-evaluation), and the structured log is the shared context that makes it all work. Completion is deterministic because Conductor knows exactly how many tasks it dispatched and can check the log for resolution entries.
